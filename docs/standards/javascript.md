# JavaScript and TypeScript

## TL;DR

- All new front-end code is **TypeScript** with `strict: true`.
- **pnpm** is the only package manager. `pnpm-lock.yaml` is committed. The `packageManager` field of `package.json` pins the pnpm version.
- **Node.js 24 LTS**, pinned in `.nvmrc` and `engines`.
- **ESLint** (flat config) for code quality and **Prettier** for formatting. **Vitest** and **Testing Library** for tests; **Playwright** is optional for end-to-end tests.
- Every project has the scripts `lint`, `format:check`, `typecheck`, `test` and `build`, so the reusable `node-ci.yml` workflow works without configuration.

Templates: [`templates/js/`](../../templates/js/).

## Rules

### JS-001: New front-end code is TypeScript with `strict: true`

**MUST** · Level 1 · Verified by: `pnpm run typecheck` (`tsc --noEmit`) in `node-ci.yml` (automatic)

- `tsconfig.json` has `"strict": true`. The template also enables `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes` and `noImplicitOverride`.
- Existing JavaScript projects migrate file by file: set `"allowJs": true`, rename one `.jsx` file to `.tsx` per PR, and never add a new `.js` or `.jsx` source file.

**Why:** types catch many bugs before the browser does, especially at the boundary with the back-end API.

**Examples:**

- ✅ `src/services/api.ts` with typed request and response objects.
- ❌ `src/services/api.js` that returns `response.data` without a type.

### JS-002: pnpm is the only package manager, and its lock file is committed

**MUST** · Level 1 · Verified by: `pnpm install --frozen-lockfile` in `node-ci.yml` (automatic); no `package-lock.json` or `yarn.lock` (manual)

- `package.json` has a `packageManager` field, for example `"packageManager": "pnpm@12.18.0"`. CI reads it through `pnpm/action-setup`.
- `pnpm-lock.yaml` is committed. `package-lock.json` and `yarn.lock` are deleted.
- Install pnpm with corepack on Node 24 (`corepack enable`), or with the [standalone installer](https://pnpm.io/installation). Node.js 25 and newer do **not** ship corepack any more; on those versions run `npm install --global corepack` or use the standalone installer.

**Why:** pnpm is fast, saves disk space with a global store and refuses undeclared dependencies. One lock file means one set of versions. See [ADR 0005](../adr/0005-pnpm-for-javascript-projects.md).

**Migrating from npm:**

```bash
corepack enable
pnpm import            # creates pnpm-lock.yaml from package-lock.json
rm package-lock.json
pnpm install
# then set "packageManager" in package.json, update CI, Dockerfile and README
```

### JS-003: The Node.js version is pinned to 24 LTS

**MUST** · Level 1 · Verified by: `node-version-file: .nvmrc` in `node-ci.yml` (automatic)

- `.nvmrc` contains `24`.
- `package.json` contains `"engines": { "node": ">=24" }`.
- Dockerfiles use a `node:24-…` base image.

**Why:** the same major version everywhere avoids "works on my machine" problems. Node.js 24 is in maintenance LTS until 2028-04-30. Node.js 26 became the active LTS on 2026-10-28; DAH Labs will plan the move to 26 in a later version of these standards. Odd versions (25, 27) are never used, because they are not LTS.

### JS-004: ESLint (flat config) and Prettier check every project

**MUST** · Level 1 · Verified by: `pnpm run lint` and `pnpm run format:check` in `node-ci.yml` (automatic)

- ESLint uses the flat config format (`eslint.config.js`). Next.js projects start from the config generated by Next.js; other projects start from the [template](../../templates/js/eslint.config.js).
- Prettier formats the code. `eslint-config-prettier` is the last entry of the ESLint config, so the two tools never disagree.
- `printWidth` is 100, the same as Python.

### JS-005: Tests run with `pnpm test` in CI

**MUST** · Level 1 · Verified by: `pnpm run test` in `node-ci.yml` (automatic)

At Level 1 any test runner is accepted, including `node --test`, as long as `pnpm test` runs the tests and fails on error.

### JS-006: Tests use Vitest and Testing Library

**MUST** · Level 2 · Verified by: `devDependencies` review (manual); `node-ci.yml` (automatic)

- [Vitest](https://vitest.dev/) runs unit and component tests. Coverage uses `@vitest/coverage-v8` with an `lcov` report for SonarQube Cloud.
- [Testing Library](https://testing-library.com/) tests React components the way a user uses them: by role and label, not by CSS class.
- The API is mocked in component tests (for example with [MSW](https://mswjs.io/)). Tests never call the real back end.

```tsx
it("shows the answer and its sources", async () => {
  render(<ChatPanel api={fakeApi({ answer: "Abidjan", sources: ["doc1.txt"] })} />);

  await userEvent.type(screen.getByRole("textbox", { name: "Question" }), "Capital?");
  await userEvent.click(screen.getByRole("button", { name: "Send" }));

  expect(await screen.findByText("Abidjan")).toBeInTheDocument();
  expect(screen.getByText("doc1.txt")).toBeInTheDocument();
});
```

### JS-007: `package.json` defines the standard scripts

**MUST** · Level 1 · Verified by: `node-ci.yml` fails when a script is missing (automatic)

| Script | Example | Used by |
|---|---|---|
| `lint` | `eslint .` | CI, developers |
| `format` | `prettier --write .` | developers |
| `format:check` | `prettier --check .` | CI |
| `typecheck` | `tsc --noEmit` (Next.js: `next typegen && tsc --noEmit`) | CI |
| `test` | `vitest run --coverage` | CI |
| `build` | `vite build` or `next build` | CI, Docker |

### JS-008: End-to-end tests use Playwright

**MAY** · Level 3 · Verified by: CI workflow review (manual)

For critical user journeys (ask a question, upload a document, validate meeting minutes), [Playwright](https://playwright.dev/) runs the application in a real browser. Run them in a separate job, against the application started with Docker Compose.

### JS-009: The front-end bundle contains no secret

**MUST** · Level 1 · Verified by: code review (manual); secret scanning (automatic)

Every value that the bundler reads at build time (`VITE_*`, `NEXT_PUBLIC_*`) is **public**: anybody can read it in the browser. Only put public values there, such as the API URL.

- ✅ `VITE_API_URL=https://api.example.org`
- ❌ `VITE_API_KEY=sk-…` (the key is visible to every visitor)

If the back end needs to authenticate the front end, use a session, a short-lived token issued by the back end, or a reverse proxy that adds the key on the server side.

### JS-010: The folder structure follows the framework conventions

**SHOULD** · Level 2 · Verified by: code review (manual)

**Next.js (App Router)**, as in baraza:

```text
frontend/
├── src/
│   ├── app/                 # routes: page.tsx, layout.tsx, error.tsx, not-found.tsx
│   ├── components/          # reusable UI components, one per file, PascalCase.tsx
│   │   └── layout/
│   ├── lib/
│   │   ├── api/             # typed API client, one file per resource
│   │   └── config.ts        # reads NEXT_PUBLIC_* once, with validation
│   └── test/                # test helpers and fakes
├── public/
├── eslint.config.mjs
├── next.config.ts
├── package.json
├── pnpm-lock.yaml
├── tsconfig.json
└── .nvmrc
```

**React + Vite**, the target for RAG-DataAfriqueHub:

```text
frontend/
├── src/
│   ├── main.tsx             # entry point
│   ├── App.tsx
│   ├── components/          # UI components
│   ├── features/            # one folder per feature: chat/, documents/, settings/
│   │   └── chat/
│   │       ├── ChatPanel.tsx
│   │       ├── ChatPanel.test.tsx
│   │       └── useChat.ts
│   ├── services/api.ts      # typed API client
│   └── config.ts            # reads import.meta.env once
├── index.html
├── vite.config.ts
├── vitest.config.ts
└── package.json
```

Put a single front-end application directly in `frontend/`, not in `frontend/<app-name>/`.

### JS-011: No `console.log` in application code

**MUST** · Level 1 · Verified by: ESLint `no-console` (automatic)

`console.warn` and `console.error` are allowed for real problems.

### JS-012: Type-aware ESLint rules are enabled

**SHOULD** · Level 2 · Verified by: `eslint.config.js` review (manual); `pnpm run lint` (automatic)

The template enables `typescript-eslint`'s `strictTypeChecked` configuration. It catches unsafe `any`, floating promises and unnecessary conditions.

**Note:** at the date of verification, `typescript-eslint` 8.72 supports TypeScript `>=4.8.4 <6.1.0`. Do not move to TypeScript 7 before `typescript-eslint` supports it.

- [ ] `pnpm-lock.yaml` is committed; there is no `package-lock.json` or `yarn.lock`.
- [ ] `lint`, `format:check`, `typecheck`, `test` and `build` scripts exist and pass.
- [ ] ESLint flat config ends with `eslint-config-prettier`.

- [ ] No secret in `VITE_*` or `NEXT_PUBLIC_*` variables.
